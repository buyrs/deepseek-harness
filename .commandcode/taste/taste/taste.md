# Taste
- When the user says "investigate" (or asks "can I..." / "is it possible to..."), they want a research-and-report pass first — feasibility findings, what exists, what's missing — before any implementation is attempted. The user also stages such questions ahead of major steps ("another question before we build the .dmg"), confirming they want feasibility settled before committing to a build/packaging step. Confidence: 0.7
- Dislikes the agent silently testing against fake/mock providers. When no real credentials are available, the agent should state upfront that verification will use local mocks (or ask the user for a real endpoint) instead of going down a mock-infrastructure rabbit hole — the user questioned why fake testing was happening and the agent acknowledged it should have stopped earlier. Confidence: 0.6
- Wants long, multi-session tasks to end with a self-contained continuation prompt/handoff document capturing environment facts, learned workarounds, validated steps, remaining next steps, and constraints — so the work can be resumed in a fresh session without re-discovering context. Confidence: 0.8
- Wants end users to be self-service with credentials: a "bring your own key" (BYOK) flow where the user pastes their own API key against any OpenAI-compatible endpoint, rather than bundling provider keys into the app. Confidence: 0.5
- Communicates in terse, action-oriented directives ("do it", "continue", "build the .dmg") and expects the agent to autonomously execute the full agreed plan — including multi-step setup, running services, and probing — without asking for step-by-step confirmation. Confidence: 0.7
- Feasibility claims should be proven empirically, not asserted: when asked to confirm something works locally, actually run install/build/launch and probe the running app, then report concrete evidence (exit codes, HTTP probes, logs). The user's "continue" pushed for completing the hands-on verification rather than stopping at the written report. Confidence: 0.5
